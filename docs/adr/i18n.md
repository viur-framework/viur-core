## Seam
Python: `translate(key, defaultText, hint, force_lang=..., public=...,
default_variables=...)`, cast to `str` or called to substitute variables.
Jinja: `{% translate "key", "default", "hint", var="x" %}`
(`TranslationExtension`) or the `translate()` function for dynamic keys.

Storage: `conf.i18n.sources` holds `TranslationSource` instances, loaded in
order by `initializeTranslations()` once per instance; the default is
`StaticModuleSource()` (the tables in `viur.core.languages`) followed by
`DatastoreSource()` (the kind `viur-translations`, managed by the
`_translation` module). A later source replaces an earlier one *per key*, not
per language.

Multi-language bone values reach templates as a `LanguageWrapper`, which
resolves against the request language. Public keys (`public=True`) are
retrievable without a session; access to everything else is decided by
`conf.i18n.dump_can_view`.

## Rules
- Keys are lower-cased. Everything else about them is your convention.
- Configure `conf.i18n.available_languages` and `language_alias_map` before
  `initializeTranslations()` runs: `normalize_translations` drops every
  language that is not an available dialect, plus empty values, on load.
  Adding a language later does not bring them back. `force_lang` must be an
  available dialect (ValueError).
- Resolution order is the requested language, then each of
  `conf.i18n.fallback_languages` in order, then the default text - where the
  default text from the source (`_default_text_`) wins over the `defaultText`
  passed in code. Aliased languages inherit their main language's value
  (`merge_alias`).
- `add_missing_translations` writes to the datastore - it is a development aid.
  `AddMissing.NEVER` / `AddMissing.ALWAYS` override the config per call site
  (errors use NEVER for exactly that reason).
- Never use a `translate` object as a dict key or compare it. Cast with `str()`
  at the point of use, because resolution depends on the current request.

## Traps
- `DatastoreSource.load` uses `run(10_000)`. More translations are silently
  dropped, and datastore edits only take effect after a restart. A source that
  raises is re-raised by `initializeTranslations` and takes the instance down.
- A source replaces a key wholesale: a datastore entry carrying only `de`
  hides the `en` value that the static table provided for the same key.
- The Jinja extension resolves at *compile* time: default text and the
  translation dict are baked into the compiled template. Newly added
  translations do not appear in already-compiled templates.
- Variable substitution is a plain replace of `{{name}}` - no escaping, and
  unknown placeholders stay in the output verbatim.
- With `conf.i18n.auto_translate_bones` (default on), a bone's `descr` and
  `params["category"]` are `translate` objects, not `str`.
- `LanguageWrapper.__bool__` is the truthiness of the *resolved* string, not of
  the dict - an empty translation is falsy although keys exist.
- `LanguageWrapper.resolve()` does not use `fallback_languages`; it returns the
  first non-empty value of the *bone's* languages, so an empty German field
  silently shows the English text. Without a request language it warns and
  takes `languages[0]`.
- `add_missing_translation` is a deferred, 20x-retried task; it also writes into
  `systemTranslations` to avoid re-triggering itself, so the in-memory table
  can differ from the datastore.
- `translate.__str__` fills `translationCache` on first use with the *same
  dict* that `systemTranslations` holds (`merge_alias` mutates it in place).
  The cache holds all languages, so a later language switch still works - but
  `force_lang` is fixed at construction, and a key that was missing on first
  use stays missing for that object forever, even after
  `add_missing_translation` added it.
- Passing a `translate` object as the `key` unpacks it to the inner key and
  loses the inner `defaultText`, with a warning plus stack trace per
  construction.

## Why not
Translations are held in process memory instead of being fetched per key. The
docstring of `initializeTranslations` names this as a known scaling problem, so
do not build features that assume the datastore is authoritative at runtime.
